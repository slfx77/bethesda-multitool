# Xenia runtime observation adapter

Status: both prototype builds boot and produce complete script-dispatch captures. The follow-up build resolves Script FormIDs and supports a controlled player `GetDead` query; both live checks passed. General gameplay actions and evaluators remain unavailable.

This overlay targets official Xenia Canary commit `c3cd8617b18ef018ea8d638c865e0cced7399846`. `prepare.py SOURCE` checks that revision, copies the owned adapter files, and adds guest hooks, lifecycle integration and successful-open file observations. It does not modify Sample inputs.

The existing BMT runtime CLI connects through `BMT.Runtime.<host-pid>` using protocol v1. The pipe admits the current user only and rejects remote clients. Hello distinguishes the host executable identity (added by the managed connection) from `guestExecutableSha256` and `guestBuildIdentity`.

## Observation boundary

Three observation hooks are available per profile: `Main::RunScripts`, `ScriptRunner::Run`, and `ScriptRunner::EvaluateLine`. The HIR builder emits an existing Xenia host builtin through `ContextBarrier` / `CallExtern` at each checked guest instruction address. This avoids the stock debugger breakpoint handler's mandatory suspension of all guest threads. Observation does not replace a game function. The separately requested `player-get-dead` action invokes the verified condition handler on a guest script thread.

`guest-probe` events contain the actual guest thread ID, PC, link register, registers r3–r10, and a bounded raw prefix at the Script-pointer argument. EvaluateLine additionally records its PDB-confirmed `SCRIPT_OUTPUT` opcode, bytecode offset and current line arguments; the enum includes flow and function opcodes. The 2011 caller and entry retain this ABI. Raw prefixes are not decoded into guessed quest, actor, condition or combat values. Dispatch entry does not prove successful execution or a gameplay outcome. The wire `frame` counter explicitly means `Main::RunScripts` entries, not rendered frames.

Start/stop/cancel change host capture state on the pipe server; they call no guest function and do not wait for a guest probe. Console commands and numeric evaluation return an unavailable error. The event queue is bounded to 4096 items; data loss increments the protocol drop counter, while control acknowledgements take priority. Connection generations and capture epochs exclude late observations from a previous session. Pipe operations are nonblocking so shutdown does not depend on a client reading. Loading a second guest in the same emulator instance is rejected; restart the process for another experiment.

Hello retains each probe's compiled state and observed hit count. A validated address/prologue and a successful handshake establish profile admission, not execution of the probe. A complete zero-event capture is not evidence that a script ran.

Script identity requires executable-specific header instructions, Script/TESForm RTTI, the expected vtable/type, and two agreeing identity reads. Only a resolved identity emits `engineScriptFormId`; anonymous, changed, or unreadable headers retain their status. Runtime IDs cannot join plugin records without a verified active load order.

Protocol kind 9 accepts only `player-get-dead` during an active capture. It queues a call for a real ScriptRunner guest callback, validates the player singleton's vtable and FormID `0x14`, uses private result storage, and restores the full PPC context after calling the verified handler. The result preserves both the handler's boolean return and finite numerical output; `comparisonObserved` remains false. It does not recover a CTDA owner or comparison. Stop/cancel emits terminal errors for queued and in-flight requests; late results cannot enter another capture. The matching managed scenario action is `read-condition-probe`. `condition-smoke.py PID NEW-OUTPUT.json` checks query rejection, a real handler result, and exactly one terminal result/error for each accepted query before cancellation acknowledgement. Run it only against an isolated admitted guest; it invokes the verified handler.

## Backing-file binding

The next native generation observes successful plugin opens and hashes the same handle with bounded offset reads, outside capture/map locks. Final path, length, write time, volume and file ID must agree before and after hashing. A failed or changing read retains its status. The cache keeps distinct identities as separate candidates, with a 512-observation limit; files over 1 GiB remain unavailable. This is a metadata-consistent handle observation, not an atomic file snapshot.

Before launching, prepare an independent manifest with `runtime guest-prepare --emulator EXE --guest XEX --data DIR --output NEW.json`. This pins candidate files, not load order. Use `runtime capture --pid PID --guest-manifest NEW.json --output NEW.ndjson` afterward. The controller requires the admitted emulator/guest identities, actual engine slot/name query, exactly one verified read-only open-handle candidate per active plugin, and freshly unchanged manifest files. Only that combination supplies complete active plugin hashes to the shared source matcher. Extra candidate files do not become loaded plugins. An incomplete query, alternative backing, changed file or missing evidence stays unbound.

Namespace payloads over 60 KiB become an explicit partial query with no promoted entries. A final 64 KiB wire guard emits a bounded error and records the lost event.
