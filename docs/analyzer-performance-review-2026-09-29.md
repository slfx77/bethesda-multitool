No explicit fix for this checkout's memory failure was established from the release notes. Availability of updates is not evidence of a speedup.

The strongest configuration findings are:

1. **The compiler was deliberately constrained.** The shared [build coordinator](../shared/Multitool.Shared/tools/scripts/Multitool.Build.psm1) computes an automatic heap cap when `CompilerHeapCapGB=0`; zero does not mean unlimited. Reproducing its plan with the previous run's 12.1 GB available-memory input returned `DOTNET_GCHeapHardLimit=0x180000000`, exactly **6 GiB**, along with `DOTNET_GCConserveMemory=7`, `DOTNET_gcServer=0`, and four MSBuild nodes. The coordinator sets these in the child build's environment and restores them afterward. This is consistent with the previously observed roughly 6.6 GB process working set and out-of-memory exceptions, but no heap trace proves the dominant allocation source. A GC heap cap is not a process working-set cap. Microsoft's documentation confirms that [memory conservation trades memory for more frequent collections and possibly longer pauses](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector#conserve-memory).

2. **The active ILLink work is single-file analysis.** Live project evaluation and the compiler's generated analyzer configuration both report `EnableTrimAnalyzer=false`, `EnableSingleFileAnalyzer=true`, `PublishTrimmed=true`, `PublishSingleFile=true`, and `SuppressTrimAnalysisWarnings=true`. Thus setting `EnableTrimAnalyzer=false` again would not help. The upstream [DynamicallyAccessedMembersAnalyzer implementation](https://github.com/dotnet/runtime/blob/v10.0.12/src/tools/illink/src/ILLink.RoslynAnalyzer/DynamicallyAccessedMembersAnalyzer.cs) registers dataflow work before its trim-only branch; its implementation is shared by single-file, trimming, and AOT checks. The analyzer name in the OOM log does not mean trimming diagnostics were enabled. Keep publish/runtime options intact when experimenting with analyzer scheduling; `PublishTrimmed` also changes runtime features, as described in [Microsoft's trimming options](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/trimming-options).

3. **Fast/full mode changes invalidate incremental builds.** The installed SDK's `Roslyn/Microsoft.Managed.Core.targets` writes a `.BuildWithSkipAnalyzers` marker after skipped-analysis builds and supplies it as an input on subsequent analyzed builds. This deliberately prevents an earlier unchecked compilation from satisfying a full-analysis request. Alternating the two modes in the same intermediate directory therefore causes recompilation. Separate intermediate/output directories can retain both caches, provided paths are configured early and project references remain isolated correctly. Merely hiding warnings or deleting this marker would defeat the correctness check.

4. **A successful build did not guarantee completed analysis.** The previous build's seven original `AD0001` entries include six ILLink OOM exceptions and one Sonar OOM exception. The warning summary repeats those messages; it is not fourteen independent failures. The build still returned zero compilation errors. Full validation should treat `AD0001` as an error so failed analysis cannot masquerade as a clean quality check. The throwing analyzer is not necessarily the component responsible for most memory allocation.

I recommend this sequence:

- Profile one forced main-project compilation with `ReportAnalyzer=true`, detailed verbosity, and a binary log; sample compiler private bytes/working set and GC activity separately. [ReportAnalyzer reports execution timing](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-options/errors-warnings#reportanalyzer), not memory attributed to each rule. A no-op incremental build cannot provide useful analyzer timings.
- Compare concurrency controls while retaining every enabled analyzer. `-MaxNodes 1` or `2` limits simultaneous projects; a compiler response file containing `/parallel-`, supplied through an absolute `CompilerResponseFile` property, controls concurrency inside Roslyn itself. This distinction matters because the previous OOM occurred inside one large main-project compiler. Hold the cap at the reproduced 6 GiB for the initial concurrency comparison, then separately test sufficient headroom, such as 8 GiB when memory permits. Do not raise all caps while continuing overlapping heavy builds. The coordinator currently permits two build slots and validates `MaxConcurrentBuilds` as two; passing one is not a supported serialization switch.
- Compare the same build after the Sonar upgrade, then evaluate Roslynator separately. The 4.16.1 update is a smaller migration; 5.0 requires review of changed/retired diagnostics. Change one variable per measurement.
- Keep .NET, Sonar, Roslynator, and xUnit code checks available during development. If profiling confirms the packaging analyzer dominates, provide an explicit development profile that defers single-file analysis to a required CI/publish check. Establish that check first, including intentional trimming-warning handling; the current broad trim-warning suppression is not a full trimming-quality gate.
- Give iteration and full-analysis builds independent intermediate/output caches. Continue running tests with `--no-build` only after verifying the relevant build is current.

Avoid assuming `-p:ConcurrentBuild=false` works: the installed .NET 10.0.401 C# targets do not pass that property to the compiler task. They do pass `CompilerResponseFile`; the installed compiler supports `/parallel-`. Roslyn's [batch analysis scope](https://github.com/dotnet/roslyn/blob/main/src/Compilers/Core/Portable/DiagnosticAnalyzer/AnalysisScope.cs) takes compilation concurrency into account. This response-file route was verified from the installed targets/compiler help and upstream code, not benchmarked here. Do not suppress broad rule categories, mark handwritten code as generated, or suppress analyzer exceptions simply to improve the timing.

Expected benefit remains unmeasured. The verified result is that updates exist and several concrete configuration choices can explain the current cost. The next useful experiment is a profiled build with all rules retained and fewer compiler processes, followed by isolated version/configuration comparisons.
