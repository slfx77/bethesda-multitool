# TB1 Shared thumbnail-loader adoption prerequisite

The prospective BMT image-gallery patch is **unapplied**. It may not remove the existing live `AssetBrowserThumbnails` counters or memory-pressure trimming. The current application keeps its working loader/cache until the Shared owner supplies equivalent observable cache behavior or a reviewed staging approach preserves it. This note proposes a small addition to existing Shared types; it does not authorize or implement Shared changes and does not claim build, test or GUI acceptance.

The Foundation owner supplied exact Shared checkpoint `20e4e2c0fb2d304ed60c05e48d8c97a9a730b684` on September 20. Its recorded portable and native checks cover real cache observations, trimming and retained retirement. BMT retains `88326240` and its existing loader pending deliberate adoption and consumer checks. The owner evidence does not establish BMT gallery or Diagnostics parity. The reviewed API and lifecycle semantics are described in that commit's `docs/thumbnail-cache-observation.md`.

## Existing authorities and required preservation

[`ThumbnailCache`](../src/BethesdaMultitool/Core/AssetBrowse/ThumbnailCache.cs) wraps Shared `BoundedLruCache<ThumbnailKey, RgbaThumbnail?>`. It registers one `ResourceCategory.CpuCache` resource with priority 20 and `TrimAffinity.AnyThread`, reports actual entry/byte/hit/miss/eviction counters, trims to half of observed resident bytes for ordinary pressure or zero for aggressive pressure, and returns the actual estimated bytes released. Its current limits are 2,048 entries and 64 MiB. Null results are genuine cached negative entries, charged at least one byte. Counters remain cumulative when source replacement clears the cache.

Pinned [`ThumbnailLoader<TReference>`](../shared/Multitool.Shared/src/Slfx77.Multitool.WinUI/Images/ThumbnailLoader.cs) already owns the correct queue, generation and asynchronous drain behavior. Its private [`ThumbnailSession<TReference>`](../shared/Multitool.Shared/src/Slfx77.Multitool.WinUI/Images/ThumbnailSession.cs) has a real `BoundedLruCache<TReference, ThumbnailContent?>`, currently limited to 1,024 entries / 32 MiB. It exposes neither counters nor pressure trimming. Retaining a second BMT cache would duplicate decoded payloads; registering an empty or estimated stand-in would misreport resource use. Neither is proposed.

## Proposed public surface for Shared-owner review

Extend `Slfx77.Multitool.WinUI.Images.ThumbnailLoader<TReference>` with:

```csharp
public CacheStatistics CacheStatistics { get; }
public long TrimCacheToBytes(long targetBytes);
```

Reuse the existing `Slfx77.Multitool.Core.Caching.CacheStatistics` return type and underlying `BoundedLruCache.Statistics` / `TrimToBytes`; do not expose entries, decoded pixels, source callbacks or a mutable cache object. Add optional constructor cache limits (names proposed: `maximumCacheEntries`, `maximumCacheBytes`) while retaining the existing Shared defaults and three-argument call. BMT would explicitly pass its established 2,048 / 64 MiB limits. The original 512-request queue remains unchanged. This is configurable memory-cache capacity, separate from the accepted persistent disk budget.

Required semantics:

- **Actual observations:** current `Count` and `Bytes` cover every still-retained cache owned by that loader, including detached sessions awaiting drain. `Hits`, `Misses` and `Evictions` remain cumulative for the loader lifetime after successful retirement. Negative results and diagnostic retention use the existing real cache charge; no invented zeroes, estimated hit rates or requested-versus-released substitution. Document the existing individually atomic counter semantics rather than promising a transactional snapshot across counters.
- **Any-thread pressure:** `TrimCacheToBytes` rejects a negative target and trims actual retained caches through their existing synchronization. It returns the sum of bytes actually removed during that call, not an observed-before/after difference that counts concurrent decoding. A producer may repopulate after trimming. Pressure must not cancel a source, clear a realized bitmap, change selection, re-run a decoder, dispatch to UI, or acquire a browser lease.
- **Replacement and failure:** stats/trim remain safe while `BeginContentSession`, `ClearSessionAsync` or `DisposeAsync` publishes/detaches sessions on the owning UI thread. Detaching a session must not make its retained payload disappear from diagnostics before its cache clears. Do not drop its observability after a failed drain, retry cleanup implicitly, or turn a failed retirement into success. Successful final disposal leaves zero resident bytes/entries and the actual final cumulative counters readable; trimming a fully retired loader returns zero.
- **Lock/lifetime boundaries:** bookkeeping snapshots references under a short internal gate, then uses existing cache synchronization without waiting under the bookkeeping gate for worker drain, cancellation callbacks, UI dispatch or user code. Concurrent retirement cannot double-count a session or its final counters. Source/session references disappear after their real retirement; retaining scalar diagnostic totals must not retain old decoders or private payloads. Lifetime/retirement methods remain UI-thread-owned; only stats/trim receive the explicit any-thread contract.

Expected Shared implementation files are `WinUI/Images/ThumbnailLoader.cs`, `WinUI/Images/ThumbnailSession.cs` and focused Shared tests; an internal helper is reasonable if needed for ownership bookkeeping. The existing Core `CacheStatistics` and `BoundedLruCache` APIs already supply the required primitives. Shared's owner should choose internal organization and tests; no BMT type or dependency belongs in Shared.

After that API is adopted, BMT's `AssetThumbnailLoader` can expose the real Shared observations to a thin existing `ResourceRegistry` adapter. The adapter retains the established name/category/priority/any-thread policy and limits, maps fields directly, and requests half/zero trims. It owns no second cache. If BMT keeps one loader per source attachment, the browser must retain and sum actual retired scalar counters in its stable diagnostic registration; alternatively one browser-owned Shared loader can be cleared and drained before changing its decoder. That composition choice must preserve source leases and final registration snapshots, not reset accounting accidentally.

## First launch, persistent cache and adoption gates

The first-launch default is confirmed from public pinned code: [`ThumbnailGallery.ViewMode`](../shared/Multitool.Shared/src/Slfx77.Multitool.WinUI/Browsing/ThumbnailGallery.xaml.cs) starts at `BrowserViewMode.Thumbnails`; `BrowserFilterToolbar.InitializeAsync(gallery, localization, settings)` delegates to `BrowserViewSelector.InitializeAsync`, which calls `settings.LoadAsync(gallery.ViewMode)`. [`BrowserViewSettings.LoadAsync`](../shared/Multitool.Shared/src/Slfx77.Multitool.Core/Settings/BrowserViewSettings.cs) returns that exact fallback for missing or unknown stored values without saving it. An explicit later user choice wins over an outstanding initial read. The proposal uses browser ID `Assets.Images`, producing `Browser.Assets.Images.ViewMode`, in `workflows.json` beside `SettingsLocation.ForApplication("BethesdaMultitool")`; theme/language retain their existing preferences file.

The accepted **512 MiB persistent** default is already available through Shared [`ApplicationThumbnailCache`](../shared/Multitool.Shared/src/Slfx77.Multitool.Core/Caching/ApplicationThumbnailCache.cs) and `ThumbnailDiskCache.DefaultMaximumBytes`. BMT persistence remains a separate prerequisite because the existing sprite decoder resolves actual companion palettes through VFS precedence. Keys must include the actual primary/companion inputs and rendering recipe, not display names or an assumed palette. No local duplicate disk cache is needed.

Required Shared evidence includes actual positive/negative cache hits and evictions, concurrent trim/decoding, exact released-byte accounting, detached-session accounting through blocked/successful/failed drains, no stale source retention, unchanged source-generation publication and unchanged existing caller defaults. BMT then needs its new projection behavior tests, normal portable/Windows builds, live Diagnostics counter/pressure checks and GUI List/Thumbnail/search/selection/localization/source-replacement/shutdown acceptance. The current eight prospective portable projection cases cannot prove the native worker or GUI lifetime gates.
