The three requested articles provide these review criteria:

- **Microsoft:** fast, isolated, repeatable tests; meaningful inputs; simple test logic; parameterized examples; and testing private behavior through the public entry point. It explicitly allows thousands of tests in mature projects and cautions against treating coverage percentage as quality. [Microsoft unit testing guidance](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-best-practices).
- **Abseil / Software Engineering at Google, chapter 12:** tests should survive internal refactoring, exercise behavior through appropriate interfaces, and expose understandable inputs and outcomes. Some duplication is worthwhile when it keeps tests clear; overgeneralized helpers can obscure their intent. [Chapter 12](https://abseil.io/resources/swe-book/html/ch12.html).
- **IBM:** isolation, deterministic results, small focused tests, meaningful names, positive/negative/boundary coverage, CI, and restoration of the test environment. [IBM's 11 practices](https://www.ibm.com/think/insights/unit-testing-best-practices).

These are guidance, not interchangeable rules. IBM encourages mocks and gives a coverage range; Abseil favors real collaborators when practical, and Microsoft cautions against coverage targets. Neither adding mocks everywhere nor deleting cases to reach an arbitrary number follows from this reading. One behavior can require multiple assertions.

The strongest findings, in priority order:

1. **Some tests cannot detect a Bethesda implementation regression.** [ShadowComparisonPcfTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Nif/Rendering/Shaders/ShadowComparisonPcfTests.cs:108) has nine theory rows comparing `stored < reference` with `reference > stored`, both calculated inside the test. Its earlier fact at line 76 evaluates 10,001 fractions using two test-local formulas. [GpuTonemapSettingsTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Nif/Rendering/Gpu/GpuTonemapSettingsTests.cs:348) contains two additional arithmetic-only facts. These may document a derivation, but they do not compare a shipping implementation against the derivation. Replace them with actual kernel/render output checked against independent expected values, or preserve the derivation as documentation and retire the standalone cases. Parameterizing this kind of test adds no production protection.

2. **Source assertions require harmless implementation details to stay unchanged.** [ResetViewKeybindSourceContractTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/App/ResetViewKeybindSourceContractTests.cs:89) requires an exact expression-bodied event handler. Changing it to an equivalent block body fails the string predicate. [WorldViewSettingsOrganizationSourceContractTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/App/WorldViewSettingsOrganizationSourceContractTests.cs:85) uses another member's documentation comment as an extraction boundary. These conflict directly with Abseil's refactoring criterion. Where practical, move neutral policies into callable code and check the resulting state. Keep narrowly justified architecture, ABI, XAML, and GPU contracts; the existence of source checks alone is not grounds to delete them.

3. **Known format values are tested through a private implementation.** [BsaWriterFlagsTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Bsa/BsaWriterFlagsTests.cs:150) invokes private `HashPath` by reflection. Preserve the known vanilla hash values, but assert the bytes emitted by `BsaWriter.Write(Stream)`. A private rename should be harmless, while incorrect archive output should fail. This applies the Microsoft public-entry-point guidance without losing the valuable format oracle.

4. **Some claimed coverage lives entirely in test helpers.** [FileHeaderParsingPerformanceTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Performance/FileHeaderParsingPerformanceTests.cs:130) checks unreadable-file handling implemented in its own private helper; the catch is at line 215. Its directory-scan facts also exercise test-owned scheduling/enumeration. Production header classifiers do run in this file and already have direct theories. Exercise the actual shipping scan/error path, or remove the helper-only assertions and unnecessary filesystem setup.

5. **A concurrency test's assertion cannot distinguish its named behavior.** [NonPumpingParallelTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Orchestration/NonPumpingParallelTests.cs:182) claims work balancing, sleeps for 120 ms, then checks only the final item count. A static partitioner or serial loop that completes all work passes. Use explicit coordination and assert other items finish while the first item remains blocked. [TextureResolverSingleFlightTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Nif/Rendering/Gpu/TextureResolverSingleFlightTests.cs:45) similarly relies on a 100 ms delay without establishing that all intended contenders reached the cold path. These are confirmed weaknesses of the assertions/setup, not observed flakes.

6. **Category enforcement accepts the wrong category.** [TestCategoryConsistencyTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Helpers/TestCategoryConsistencyTests.cs:41) accepts `TestCategories.\w+` for every guard and searches an entire file. A GPU guard paired with BucketB therefore satisfies the predicate. The in-memory reproduction confirmed this. [IngredientParserTests](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Esm/Parsing/IngredientParserTests.cs:12) also applies BucketB to a class containing a synthetic theory. Validate the corresponding category at the actual class/method scope and separate synthetic from retail classification. This makes the existing CI/filtering strategy more trustworthy.

7. **Opt-in GPU fixtures expose process-wide configuration to parallel tests.** [ReferencePipelineGpuFixture](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Core/Formats/Nif/Rendering/D3D12/ReferencePipelineGpuFixture.cs:289) temporarily changes the scene-sample environment variable. Inject the sample-count option or use the existing [ProcessEnvironmentGroup](C:/dev/Multitool/BethesdaMultitool/tests/BethesdaMultitool.Tests/Helpers/ProcessEnvironmentGroup.cs:27) pattern.
